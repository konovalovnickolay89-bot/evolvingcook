# Evolving Cook — UX evaluation and whole-app optimisation plan

**Date:** August 2026
**Evaluated build:** `3b1e520` (station running-chef log and choose-station home)
**Contract:** 0.1.18 (`src/contract.ts:5`, `backend/docs/openapi.json`)
**Author:** UI/UX pass for Mykola (running chef, Hilton London Wembley)
**Status:** evaluation only — **no restyling or IA changes are made in this PR**

---

## 0. How to read this

Section 1 is the inventory: every screen, every feature, every customisation control, with
file references. Section 2 walks Mykola's real fast paths and measures them. Section 3 lists
what fights service speed, worst first. Section 4 proposes the information architecture and
Section 5 the customisation model. Section 6 is the sequenced build plan — five passes, no
big-bang rewrite. Appendices hold the measurements, screenshots and the contract fields the
frontend is not using yet.

Everything here is grounded in the code at `3b1e520` and in the 0.1.18 contract. Screenshots
in Appendix B were captured from the running build with the API stubbed by 0.1.18-shaped
fixtures (`scripts/ux-eval-capture.mjs`), so they show the real components, not a mock.

**Boundaries respected throughout:** KitchenCut stays the hotel book — no recipe authoring,
allergen master or supplier catalogue browsing here. Buzz/Mise stays the place for talking
and tips. Cook is tickets, 86s, prep, fridge, orders. Assist stays silent and card-shaped;
there is no chat anywhere in this plan.

Two things stand out. First, **every server-side customisation is one-shot**: the mode prompt
is the only door and it closes after the first answer. Second, **the client-side memory is
observational, not active** — the app remembers the last station but still makes the chef pick
it, and forgets the day, the face and the filter he was using ten minutes ago.

### 1.7 Platform

Dark Tokyo Night Storm token set, IBM Plex, hand-written CSS, no Tailwind
(`src/styles/tokens.css`, `app.css`). Shell is a single 40 rem column
(`tokens.css:58`) centred at any width. PWA with prompt-style updates, five-minute update

`forceRefresh.ts`). Bearer token in `localStorage`, never cookies; Dexie is never cleared on
401 (`tokenStorage.ts`, `db/index.ts`). Two sticky banners can stack above the header:
contract skew and app update.

## 2. The running chef's day, measured

Measurements from `scripts/ux-eval-measure.mjs` on a 390 × 844 phone viewport (iPhone 14
class), Skybar ordering board, nine dishes, **and an empty station log** — the friendliest
possible case.

### 2.1 Skybar tonight — "open the day, tick what is on, hide the rest"

| Step | Action | Cost |
|---|---|---|
| 1 | App opens on Choose station. Day defaults to today | — |
| 2 | Tap **Skybar** | tap 1 |
| 3 | Station log screen loads; scroll past Fill from kitchen, seven kind chips and the four-field add form | scroll |
| 4 | Tap **Continue to board** | tap 2 |
| 5 | Board loads. Face toggle, progress strip, Update menu and the *same station log panel again* sit above the menu. First dish row starts at **y = 876 px on an 844 px screen** | scroll — no dish is on the first screen |
| 6 | Tap the dish row to expand | tap 3 |
| 7 | Tap **86** | tap 4 |
| 8 | Tap the row again to collapse the ingredient list and note field | tap 5 |
| 9 | Each tick invalidates and refetches the whole board; the row is disabled until it returns (`BoardPage.tsx:162-173`) | round trip |

So: **two taps and two scrolls before the first dish, then four to five taps per 86.** And
"hide the rest" is not possible — there is no filter, search or sort on the board.

### 2.2 The other five, briefly

* **Breakfast buffet** — replenish against par. Rows show par / on-hand / top-up
  (`lineDisplay.ts:73-79`). Same log wall above the list. No "only items under par" view.
* **À la carte** — same shape as Skybar, and the same 86 problem, on a much longer menu.
* **Banquet buffet / Banqueting** — covers field and Scale produce sit *below* the log panel
  on the board (`BoardPage.tsx:338`), so the first thing the chef needs on a banquet day is
  the third thing on the screen. `prep_plan` and `qty_draft` — the entire guided experience —
  never render.
* **Canteen** — produce with counts works as designed; the `morning_qty` / `qty_draft` strip
  that would propose the numbers is not mounted.

## 3. What fights service speed

Ordered by cost to Mykola during service.

### 3.1 An 86 is invisible on an ordering board — the Skybar screen's whole job

`BoardLine.tsx:137-140` passes the `check` state to the row **only when the section is not in
ordering mode**. `BoardRow.tsx:90` derives its 86 styling from that same prop
(`is86 = mode === "check" && check === "86"`). Net effect on Skybar and à la carte: an 86'd
dish renders identically to an available one. Measured: `rowsFlaggedEightySix: 0` in ordering
mode versus `1` in counts mode, on the same fixture. The progress strip says "1 86" but never
says *which*. The chef has to open rows one at a time to find it.

Compare Appendix B shots `04` (ordering — Truffle arancini is 86 and looks normal) and `07`
(mode unset — the same row is red and reads 86).

### 3.2 "Tick what is on" is not available in ordering mode

The tri-state Present / Confirm / 86 control is inside a `!ordering` guard
(`BoardLine.tsx:153`); ordering mode gets a single 86 chip (`:197-208`). The contract rule is
that ordering mode must not show *count* UI (`FE-SECTION-MODES.md` §7.6) — Present/Confirm are
status, not counts, so this is an over-application. Mykola's stated Skybar path is "tick what
is on"; today he can only mark what is off.

### 3.3 The station log is a wall in front of the board, and then it repeats

The log is a whole screen between the picker and the board (`App.tsx:229-237`), and then the
same panel renders again on the board (`BoardPage.tsx:331`). Measured height of the compact
panel with **zero** log rows: 491 px, starting at y = 335. That is what pushes the first dish
to y = 876. With three open rows (Appendix B shot `04`) the board is roughly a screen and a
half down.

The log's internal order compounds it: the compose form comes before the log content, so the
default reading is "fill in a form", not "here is what is outstanding".

### 3.4 The Prep / Service toggle changes nothing

`face` is threaded from `BoardPage.tsx:48` into `BoardLine`, where it only appends a CSS class
(`BoardLine.tsx:120-121`). There is no `.board-line--service` rule in `src/styles/`. Row
rendering keys off `line.mode`, never the face. The toggle changes one word in the lead line
and the section label. It occupies the most valuable strip on the screen — a full 44 px row
directly under the title — and teaches the chef that the toggle is meaningless.

### 3.5 Bottom-nav "Station" throws away the station

`App.tsx:150` explicitly refuses to navigate to `board`, so the Station tab always lands on
Choose station. Mid-service, going to Walk to count a fridge and coming back costs the full
picker → log → board sequence again. The app knows the last station (`contract.ts:39`) and
still does not use it for anything but a chip.

### 3.6 The assist review queue has no door

`#/inbox` is only reachable by typing the URL. There is a fully styled inbox button with an
unread badge in the CSS (`app.css:896-927`) with no markup behind it. So: notes get parsed
silently, proposals accumulate, and the accept-target model (today only / every day /
permanent) — the thing that makes assist trustworthy — is never seen. Its back link still says
"← Day home", a screen that no longer exists (`InboxPage.tsx:114`).

### 3.7 Assist depth is written but not mounted

`order_assist`, `qty_draft` and `prep_plan` arrive on every board GET and are dropped on the
floor (§1.8). For Skybar this is the "what to order" half of the section's stated purpose. For
banqueting it is the entire guided prep plan.

### 3.8 The board is online-only while the walk sheet is offline-first

Dexie holds walk lines only (`db/index.ts`). Every board tick is a network round trip with a
full board invalidation and no optimistic update. In a cellar or a lift lobby the walk sheet
keeps working and the board stops. A 401 is worse: `apiRequest` never auto-refreshes
(`client.ts:35-91`) — only `WalkPage.syncBatch` does — so an expired token turns every board
action into "Session expired" until the chef finds the Account chip.

Related: `refetchOnWindowFocus: false` globally (`main.tsx:13`) and no polling on the board,
so a PWA resumed from the pocket shows yesterday's fetch with no staleness cue.

### 3.9 Hash routing is doing more work than it should

Route state exists twice (URL and React state, `App.tsx:74-125`), navigation pushes new hash
entries instead of using history, so Back walks a growing stack; `#/orders/1,2,3` puts ids in
the URL; a 4-second interval polls for token presence (`App.tsx:127-140`). Nothing here is
visible to Mykola directly, but it is why "go back to my board" is unreliable and why every
new surface (inbox, settings) needs bespoke plumbing.

### 3.10 One 40 rem column on a kitchen iPad

`--shell-max: 40rem` (`tokens.css:58`) centred at every width. At 1024 × 768 the visible
screen is header, toggle, strip, Update menu and the top of the log form — **zero dishes**
(Appendix B shot `11`). The mounted iPad is the screen the section actually reads from during
service, and it is showing a phone.

### 3.11 Smaller things worth folding into a pass

* "Update menu" is a destructive-sounding regenerate with no confirmation, permanently parked
  above the board (`BoardPage.tsx:305`).
* Covers/Scale for banquet is below the log panel instead of in the header.
* No area picker on Walk, though `WALK_AREA_LABELS` including "Skybar cellar" exists unused.
* Orders asks for a typed PO id because 0.1.18 has no PO list endpoint — a backend ask, but
  the FE can at least remember recent POs locally.
* The picker's section cards show purpose text but no counts, though `ServiceDayOut.sections[]`
  carries `line_count`.
* Both banners are sticky above the header and can stack, eating 5 rem of a 844 px screen.

## 4. Proposed information architecture

### 4.1 The model in one line

**One station screen with three faces — Board, Log, Review — reached from a station switcher
that remembers where you were.** The picker becomes a sheet, not a wall.

```
Bottom nav        Station              Walk              Orders
                     |
Station screen   [ Skybar ▾ ]  Ordering · today · 3 open        ⚙
                 ┌─────────────────────────────────────────┐
                 │  Board  ·  Log 3  ·  Review 2            │  ← faces
                 ├─────────────────────────────────────────┤
                 │  All · To order · 86 · Notes             │  ← filters (sticky)
                 │  ── assist strip, only when present ──   │
                 │  dish  dish  dish  dish  dish …          │
                 └─────────────────────────────────────────┘
```

* **Station** in the bottom nav returns to *your* station, not the picker.
* The station name in the header is the switcher: tap it for the six sections plus today /
  yesterday. Choose station stays as the first-run screen and as the switcher's content.
* Faces replace the Prep/Service toggle, which earns its place back by actually switching
  something.
* The log stops being a gate and a duplicate: it is one face, with a badge, always one tap away
  from the board and never on top of it.
* Review gives the assist queue a door and a count, scoped to this station and day, with the
  global queue still at `#/inbox`.

### 4.2 Board face composition

1. **Sticky station bar** — station name (switcher), mode pill, day, open-log badge, gear.
2. **Sticky filter row** — one line of chips, mode-aware:
   * ordering: `All · To order · 86 · Notes`
   * counts: `Left · Done · 86 · Notes`
   This is Mykola's "hide the rest", and it is the cheapest big win on the board.
3. **Assist strip** — rendered only when the payload exists: `order_assist` card (ordering),
   `qty_draft` strip (counts), `prep_plan` (counts + guided). All three components already
   exist.
4. **Line list** — the rest of the screen. First row above the fold on a 390 × 844 phone.

### 4.3 Row interaction

The current row is "tap to expand, then act". Make the collapsed row carry the state and the
primary action:

* **Ordering row:** name · `6 items · 2 to order` · **state badge** (OK / 86). Tapping the
  badge opens the three-way inline control in place; tapping the name expands ingredients,
  stock dots and the note field as today. 86 goes from four taps to two, and an 86 is legible
  from across the pass.
* **Counts row:** unchanged three numbers, with Mark done promoted to the collapsed row.

### 4.4 Log face

Read first, compose second. Open items grouped by kind at the top; the seven kind chips become
filters over that list rather than a picker for a form. A single primary **Add** opens the
compose sheet (What / Qty / Do / Store-fridge). "Fill from kitchen" moves into the sheet header
as a quiet action — it is a helper, not the headline. Walk hand-off from a `check` row stays
exactly as it is; it is one of the best interactions in the app.

### 4.5 Defaults, per section

All six work in the same frame; only the defaults differ.

| Section | Default mode | Default face | Default filter | Board emphasis |
|---|---|---|---|---|
| Skybar | ordering | Board | To order | Menu + 86 + order_assist; Skybar cellar as walk area |
| À la carte | ordering | Board | All | Menu + 86 + ingredients |
| Breakfast buffet | counts | Board | Left | Par / on-hand / top-up, under-par first |
| Canteen | counts | Board | Left | Three numbers + qty_draft (morning clocks) |
| Banquet buffet | counts + guided | Board | Left | Covers in the header, then prep_plan |
| Banqueting | counts + guided | Board | Left | Covers in the header, then prep_plan |

Recommendations still come from `mode_recommendation` and are still never auto-applied — the
prompt stays. The difference is that the mode becomes changeable afterwards (§5).

## 5. Customisation model

Three tiers. The rule: **the chef should be able to run a whole service without opening tier
three, and should be able to change anything in tier three without leaving his station.**

### Tier 1 — remembered automatically, never asked

Last station, last day, last face, last filter per section, last walk area. All local. The app
already stores the first of these and does not use it; the rest are one `localStorage` key
each.

### Tier 2 — visible on the surface it affects

Filter chips, face tabs, day switch, covers on banquet, quick-add. One tap, no menu.

### Tier 3 — the Customise sheet (the gear, per station)

* Mode: **Counts / Ordering** (+ Guided for banquet) — the missing door from §3.6.
  `getSectionSettings()` and `patchSectionSettings()` already exist.
* Default face and default filter for this station.
* Which log kinds surface as badges on the board face.
* Default walk area for this station (Skybar cellar for Skybar).
* Row density — comfortable / compact.

Global (from the Account chip): text size for glare and gloves, contract/build diagnostics
(currently only reachable when a banner happens to fire), sign out.

### Never hidden, never customised away

86 state, unsynced walk counts, contract-skew banner, and the fact that a proposal is pending.
Those are safety, not preference.

## 6. Optimisation plan

Five passes plus a bug-fix pass. Each is shippable on its own and leaves the app working; no
pass requires the next one. Rough size is given as surface touched, not calendar time.

### Pass 0 — service-safety fixes (no redesign)

**Why first:** two of these are silent correctness problems during service.

| Change | Files |
|---|---|
| Show 86 state on ordering rows — pass `check` to `BoardRow` regardless of mode, keep quantities suppressed | `BoardLine.tsx:137-140`, `BoardRow.tsx:90` |
| Restore Present / Confirm / 86 in ordering mode (status is not count UI) | `BoardLine.tsx:153-208` |
| Bottom-nav Station returns to the current station | `App.tsx:142-155`, `AppShell.tsx:57-68` |
| One automatic token refresh before surfacing a 401 | `api/client.ts:35-91` |
| Fix the inbox back link ("← Day home" → "← Station") | `InboxPage.tsx:114` |

**Acceptance:** on an ordering board with one 86'd dish, the row is visibly 86 without
expanding (`rowsFlaggedEightySix >= 1` from `scripts/ux-eval-measure.mjs`); a dish can be
confirmed on in ordering mode; Walk → Station returns to the same board; an expired token
recovers without a visit to the login screen.
**Risk:** low. No layout change, no new routes.

### Pass 1 — information architecture

**Goal:** one station screen with faces; the log stops being a gate and a duplicate.

* Merge `StationLogPage` into the station screen as the **Log** face; delete the duplicate
  compact panel from the board.
* Add the station switcher to the header; keep `BoardsPage` as first-run and as switcher
  content, with `line_count` per section from `ServiceDayOut`.
* Give **Review** a face and a badge; keep the global queue at `#/inbox`.
* Keep every existing hash URL working as an alias (`#/station/{d}/{s}/log` opens the Log
  face, `#/board/{d}/{s}` the Board face) — deep links are used by ops and by the screenshot
  scripts.
* Fold the routing duplication in `App.tsx` into one source of truth while it is open.

**Acceptance:** on a 390 × 844 phone with three open log rows, the first dish row is above the
fold; the station log appears exactly once; Review is reachable in one tap and shows a count;
all old hash URLs still resolve.
**Risk:** medium — this is the routing pass. Mitigated by keeping URLs stable and by shipping
Pass 0 first.

### Pass 2 — the Skybar station (ordering boards)

**Goal:** Mykola's stated fast path, end to end, on Skybar and à la carte.

* Filter chips: All / To order / 86 / Notes, remembered per section.
* Collapsed-row state badge with the two-tap 86 (§4.3).
* Mount `OrderAssistCard` from `BoardOut.order_assist` with Add to order / Pass.
* Mount the inline pending proposal on the row via `coercePendingProposal`, plus the
  parsing / ready note chip that `BoardRow` already supports.
* Move "Update menu" into the gear sheet with a plain-language label.

**Acceptance:** open day → Skybar → 86 a dish in ≤ 4 taps total from app launch; "To order"
shows only dishes with `to_order_count > 0`; the order-suggest card is visible without
scrolling past the log.
**Risk:** low-medium. Components exist; the work is mounting and filtering.

### Pass 3 — the other five sections

* **Counts boards:** mount `QtyDraftStrip` from `qty_draft`, including `morning_qty` clock
  times; accept-with-overlay is already implemented in the component.
* **Guided banquet:** mount `PrepPlanStrip`; move covers + Scale produce into the station
  header sheet so covers are the first thing on a banquet day.
* **Breakfast:** default filter to under-par; keep par / on-hand / top-up.
* **Canteen:** counts with the qty draft; no other change.

**Acceptance:** each of the six sections opens on a screen whose first content matches its
stated purpose in `contract.ts:30-37`.
**Risk:** low. Additive.

### Pass 4 — walk, orders, delivery

* Area picker on walk start from `WALK_AREA_LABELS`, defaulting to the station's configured
  area; keep the log-row hand-off.
* Remember recent PO ids locally so Orders is not a blank id field; keep the typed-id escape
  hatch. (Backend ask: a PO list endpoint would remove this entirely.)
* Surface unsynced-walk state in the station header, not only on the walk screen.
* Delivery unchanged.

**Acceptance:** a Skybar cellar walk starts in two taps from the station screen; Orders shows
the last POs without typing.
**Risk:** low.

### Pass 5 — visual system

Only after the IA is settled, so the restyle is applied to the final structure once.

* Density and hit targets tuned for gloves and for reading at arm's length; the token set and
  spacing scale are sound and stay.
* **iPad two-pane at ≥ 900 px:** list on the left, expanded row / log / review on the right.
  Lift `--shell-max` for the board surface only.
* Sticky-chrome budget: at most one banner plus the station bar; the rest scrolls.
* Type scale review for glare, and a global text-size control.
* Motion: keep it to state feedback on ticks; nothing decorative.

**Acceptance:** at 1024 × 768 the board shows a dish list and a detail pane in the first
screen; at 390 × 844 no more than 30 % of the viewport is fixed chrome.
**Risk:** low-medium, cosmetic but broad. Deliberately last.

## 7. Out of scope

* **KitchenCut** stays the hotel book. No recipe authoring, no allergen or nutrition master, no
  supplier catalogue browsing. Cook consumes catalogue data through the API and shows what the
  board needs; it never becomes a second book.
* **Buzz/Mise** stays the place for talking and tips. No chat, no comments, no feed in Cook.
* **Assist stays silent.** Fill-from-kitchen and note parsing run in the background; the chef
  meets the output as accept/reject cards with an explicit target. No assistant conversation
  is proposed anywhere in this plan.
